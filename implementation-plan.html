MVP v1.1

Implementation Plan

A phased build plan for the Biblical Literature Explorer, scoped to deliver a working reading-and-research MVP as quickly as possible while preserving the architectural runway for depth.

Scope

MVP Definition

The MVP delivers a readable, searchable, annotated Bible with progressive disclosure. Users can read passages, switch translations, click words to inspect them, see discovery cards, and search by natural language query. Authentication enables sync.

✓ In Scope (MVP)

  • ✓ Passage reading with translation selector
  • ✓ Chapter navigation & breadcrumbs
  • ✓ Layer 1-2 content (Read + Understand)
  • ✓ Word-level inspector panel (click to reveal)
  • ✓ Inline discovery cards
  • ✓ Search (basic + natural language)
  • ✓ Homepage with discovery surface
  • ✓ Highlights, bookmarks, personal notes
  • ✓ Google + Apple authentication
  • ✓ User preferences sync across devices
  • ✓ Responsive mobile + desktop layout
  • ✓ Static knowledge graph (entity pages)

— Out of Scope (Post-MVP)

  • – Interactive knowledge graph visualization → v1.4
  • – Multi-panel research workspace → v1.5
  • – Zoomable interactive timeline → v1.2
  • – Map viewer (Leaflet/MapLibre) → v1.6
  • – Layer 4 research tools → v1.3
  • – AI assistant / question answering → v2.0
  • – Collections and curated reading lists → v2.1
  • – Citation graph visualization → v1.3
  • – Comparison viewer (side-by-side manuscripts) → v1.3
  • – Command palette → v2.2
  • – Social / sharing features → v2.1
  • – Offline support (PWA) → v2.2

See Post-MVP Roadmap for full details on each phase.

Data Models

Passage — MongoDB

{
  book: string,
  chapter: number,
  verses: [{
    num: number,
    text: string,
    translation: string,
    words: [{
      position: number,
      hebrew?: string,
      greek?: string,
      strongs?: string
    }]
  }],
  metadata: {
    section, genre, date_range
  }
}

Entity — Neo4j

(:Entity {
  id: string,
  type: 'Person'|'Place'|'Concept'
    |'Event'|'Text'|'Artifact'|'Kingdom',
  name: string,
  slug: string,
  summary: text,
  lexicon?: { strongs, stepbible, etcbc }
})

(:Entity)-[:MENTIONED_IN]->(:Passage)
(:Entity)-[:RELATED_TO]->(:Entity)

User — MongoDB

{
  id: ObjectId,
  accounts: [
    { provider, providerId }
  ],
  preferences: {
    defaultTranslation,
    fontSize, theme
  },
  highlights: [{
    passageId, verseRange,
    color, note?, createdAt
  }],

Build

Key Technical Decisions

SSR for passages, CSR for search

Passage pages are server-rendered for SEO and instant content. Search pages are client-rendered for interactive filtering and real-time results.

Translations stored per-verse in MongoDB

Each verse document holds all translation strings. This avoids N+1 query patterns when switching translations and enables multi-translation display.

Neo4j for entity graph, not MongoDB

The entity graph is deeply interconnected (people mentioned in passages, related to concepts, located in places). Neo4j makes these traversals a single query vs. multiple MongoDB joins.

OpenSearch for full-text search, not MongoDB Atlas Search

OpenSearch provides superior Hebrew/Greek stemming, fuzzy matching, and relevance tuning. The infrastructure cost is justified by search quality for ancient languages.

Inspector panel via client-side fetch, not SSR

Loading entity data on demand (when a user clicks a word) avoids preloading the entire entity graph on every passage page. Use TanStack Query with prefetching for common words.

Redis as read-through cache layer

Passage and entity data is relatively static (changes only with translation updates). Redis caches API responses with TTL. Invalidate on translation data update events.

Design tokens as CSS custom properties

All colors, spacing, radii, shadows, and typography are defined as CSS variables in a single tokens.css. Both Tailwind and shadcn/ui consume these tokens. No hardcoded values.

Mobile-first responsive layout

Passage page uses a single-column layout on mobile, two-column on tablet+, sidebar on desktop. Inspector panel becomes a bottom sheet on mobile.

Open lexical data stack — no licensed lexicons

The platform uses Macula Hebrew (morphology, clause-level annotations), ETCBC (comprehensive linguistic database of the Hebrew Bible), STEPBible (open lexical definitions with glosses and frequency data), and Strong's (public domain). Together they replace BDB, HALOT, and TWOT — zero licensing cost, fully auditable, community-maintained. Data is ingested via ETL scripts and stored in Neo4j for entity-based queries and MongoDB for verse-level word lookups.
